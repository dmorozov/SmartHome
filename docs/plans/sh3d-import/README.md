# SH3D import, phased — series index

Four implementation phases turning `docs/plans/sh3d-dollhouse-spec-final.md` into a home-scale pipeline: Devices placed in the Sweet Home 3D drawing, positions computed instead of hand-typed, binding to the Hub through author-controlled keys — while keeping everything about the working Dollhouse that the spec would have broken.

Written 2026-08-01 against commit `d01f290`, from the adversarially-verified critical analysis of the spec (4 audits × 4 verifiers over the spec, the repo, plan 06, and the four real `.sh3d` files in `docs/examples/`). Finding IDs used throughout (EX-\*, SR-\*, SI-\*, P6-\*) refer to that analysis; each phase file restates every finding it depends on, so no phase needs the analysis itself.

**Stop rule (from phase 0) — DID NOT FIRE.** Run 2026-08-02 on SH3D 7.4: 13/13 keyed pieces survived an open-edit-Save, and SH3D re-serialised the properties from its own model (their order changed) rather than passing bytes through. Unknown `<property>` children are first-class, not tolerated debris. **Phase 1 is unblocked**; full results and the two side-findings that change it are in [phase-0 §5](phase-0-experiment-gate.md#5-recording-the-results).

*The rule as written, for the record:* if V1 had failed — SH3D dropping unknown `<property>` elements on save — phases 1 and 2 were dead as designed, their only fallback (key encoded in the piece *name*) being exactly the alternative ADR-0004 rightly rejected; phase 3 would have proceeded against today's two-file pipeline.

**Authoring, settled and built.** Devices are placed by dragging a typed marker from `SmartHome.sh3f` (generated by `panel/tool/sh3d_marker_library.py`) and typing one key into *Modify furniture → Other properties…*. `kind` arrives preset from the catalog entry; `catalogId="SmartHome#<kind>"` identifies a marker, so an ordinary bed can never look like a Device. Sweet Home 3D must be launched via **`panel/tool/sh3d.sh`** — it declares the properties through a startup flag that SH3D does not persist, and without it the key fields are invisible and uneditable (the values themselves are safe either way).

**What phase 0 changed for phase 1** (all measured, none anticipated):

- **Duplicate keys are the default, not the accident.** SH3D names every placed piece after its catalog entry, so a 13-piece drawing produced 6 distinct slugs (4× `kitchen-cabinet`, 4× `fixed-window`). D2's duplicate-key error is now the *first* thing an author will meet, not a rare copy-paste hazard — its message quality is load-bearing, and V4 (E4) no longer needs running to justify it.
- **The zero-`<level>` case is real** (EX-V14's open question): a one-level drawing writes no `<level>` element at all and no object carries a `level` attribute. Fixture `no-levels.Home.xml` pins it — and the converter already handles it (`1 floor(s), 2 room(s)`), so that path was untested rather than missing.
- **Two budgeted behaviours already work.** `negative-origin.Home.xml` converts to YAML identical to the untranslated original bar the provenance comment, so the min-shift erases the offset exactly. Phase 1 inherits both this and the default-Floor synthesis; its estimate should shrink accordingly.
- **Key spelling is unconstrained by the tool.** The first key typed in anger was `light_kitchen_1` — underscores, where every id in `devices.yaml` is kebab-case. Phase 1 must decide: accept, normalise, or reject. Validating against the loader's own slug rule puts the failure in the drawing instead of the Panel.

## Corrections to the spec (authoritative here, not there)

The spec stays on disk as reference material. Where this series and the spec disagree, this series is right, for the measured or verified reason given:

| # | Spec says | Correction | Evidence |
|---|---|---|---|
| 1 | §7: Home.xml angles are **degrees** ("Home.xml writes degrees, the Java model works in radians") | **Radians.** Inverted. 1,412 piece angles across the four example files: max = 6.2832 (2π), zero values > 6.3, clustered at float32 π-multiples (1.5707964, 3.1415927, 4.712389), arbitrary sub-2π values elsewhere. A degrees→radians conversion mis-rotates every Device ~57×. The `angle` attribute is optional (absent = 0) | EX-V5 |
| 2 | §7: negate Y, output y=north, negate angles | **Keep y-south** (ADR-0004). The whole repo — converter, domain, `plan_geometry`'s outward classification, every hand-typed position, the goldens — is y-south. Negation mirrors the house | SR-1, SR-18 |
| 3 | §9: `source.converted_at` timestamp in the artifact | Dropped. Contradicts §12's own byte-identical determinism rule, and would break the repo's byte-for-byte golden discipline | SI-1 |
| 4 | §1.2: roomKey/levelKey are author-controlled properties | **No mechanism exists in the spec** for authoring them (SI-3 — every described mechanism is furniture-only, and the backlog has no V-item for it). Phase 0 checks whether SH3D rooms/levels can carry properties at all; the expected outcome ratifies slug-of-name identity for Rooms and Floors (loud-failure semantics, per SR-7: the repo's orphan errors are noisy, not the "silent break" the spec claims) | SI-3, SR-7 |
| 5 | §5: five-tier resolver over four HA registries | **Binding table only** (one hand file). Tier 1 ("key matches an HA device ID") can never bind the current fleet — all 33 dev stand-ins are helpers/template entities with no device id (spec §3.1's own admission). The table the fleet *would* use is the one the spec never specifies (SI-6: no owner, schema, or parser). Registry tiers are a recorded future trigger: real hardware with registry entries | SI-5, SI-6, P6 verifier |
| 6 | §6: registry library, catalogId = HA device id, zero typing | Deferred. It also defeats the spec's own no-HA-IDs-in-the-artifact rule (§9/§14) by emitting device ids as keys. And catalogId is per model class, so it cannot key multiple same-kind Devices anyway — `placementKey` typed once per placement is the baseline | SI-M1, EX-V3 |
| 7 | §1/§1.1: duplicate keys legal; one key → N entities; ephemeral converter `id` beside `key` | **1 placement = 1 Device = 1 state; keys unique; key IS the id.** The spec has no aggregation rule for multi-entity keys (SI-11), its singular `hub:` block can't carry them, and per-copy consumer state is impossible under its own contract (SI-M3). The repo's one-state-per-Device model stays | SR-13, SR-14, SI-9, SI-11 |
| 8 | §9/§10: arbitrary polygons, arcs, wall footprints + openings, three profiles | Cut. Rectilinear-only stays (ADR-0004, enforced twice); Walls stay centerline segments; locks/garage doors are ordinary placements (the garage-door pin already works); compact/minimal profiles geometrically break the Rooms-tile-the-Floor invariant that `Floor.outline` and `roomAt` depend on | SR-2, SR-3, SR-M4 |
| 9 | §12: nine-module Python package, Shapely, upload service, 4xx | Cut. Stdlib-only single file with a pure core is ADR-0004's decision and plan 04's proven pattern; there is no upload seam in a one-house repo | SR-8, SR-17 |
| 10 | §4: role list | It omits 8 of the repo's 14 kinds and cannot express the StatusState family (7 of 14 kinds). The five sealed DeviceState families remain the Panel's render archetypes; the capability vocabulary is not adopted Panel-side | SR-5, P6-6 |
| 11 | §3.1: capabilities are runtime state → drive behaviour from live state | Togglability keeps the landed safety contract: "answered from the House, never from live state" (`hub_client.dart`) — it guards the thermostat from `homeassistant.toggle` flipping real HVAC | P6-4 |
| 12 | §9: artifact has no house-level name | `name:` stays — the loader requires it and the Panel header renders it | SR-M2 |
| 13 | §8: room membership tie → smallest room; `room: null` legal | Membership is computed (that is the point), but no-match is an **error** naming the piece, not a legal null — fail-fast gatekeeper posture, and Rooms tile the Floor so real ties are boundary-only | SR-12 |
| 14 | §9 schema vocabulary: `levels:`, `openings:`, "dollhouse/3.0" | CONTEXT.md wins: `floors:`, no openings, and the artifact is the House Plan (the Dollhouse is the *view*). "Placement" and "Key" get minted in CONTEXT.md in phase 1 | SR-15 |

## The empirical record (docs/examples/, all four files saved by SH3D 7.4, version="7400")

Settled by static forensics — phase files restate what they need, this is the complete table:

- **EX-V5 · angles are radians** (see correction #1). Optional attribute; absent = 0.
- **EX-V11 · group child coordinates are absolute** (529/529 children of 120 groups in plan coordinates). No transform composition. Groups never nested in the corpus; a group may lack `angle`; every child carries its own `level` equal to the group's.
- **EX-V12 · id on 100% of rooms/walls/pieces/levels/labels.** Two dialects coexist inside single files (legacy `wall0` beside uuid-style) — evidence ids survive re-saves. We never emit them (spec §12 rule kept).
- **EX-V14 · zero objects missing `level`** in any leveled file — but **no file has zero `<level>` elements**, so the synthesize-a-default-Floor path (spec §8) has no fixture anywhere. Phase 0 makes one.
- **EX-V16 · every archive carries Home.xml** plus the legacy Java `Home` entry and `ContentDigests`. No DOCTYPE in any Home.xml.
- **EX-V19 · arcExtent trap**: the only occurrences in 411 real walls are two literal `"0.0"` on *straight* walls. Test `arcExtent != 0`, never presence. Sign-vs-direction still unverified (phase 0, opportunistic).
- **EX-V20 · 0/411 walls lack `height`.** But 39 carry `heightAtEnd` (sloped tops are ordinary) and a wall's height can exceed its Floor's height (Factory: 390 on a 250 level). Irrelevant to the 2.5D Dollhouse; recorded for any future 3D work.
- **EX-V1/V2 · open.** Zero `<property>` children on ~1,700 placed pieces — the mechanism is unused in the wild, so nothing proves or refutes save/load survival. The `<home>` root carries 14–23 property elements preserved across saves (mechanism works at home scope). Phase 0's experiment is the only answer.
- **EX-V3 · catalogId on 96–100% of placed pieces, including user-imported**, in three dialects: `Creator#id` (`eTeks#shower`, `Artist373#shelves`), flattened `creator-id` (`eteks-doublehungwindow80x122` — the SH3D-Online/JS dialect), opaque 20-char tokens (`FP7oy8H1jlqexh2MwXxY`). Only in-app geometry (Shape/Roof/Beam) lacks it. Never assume the `#` shape; role-from-prefix is useless for the token dialect.
- **EX-V4 · suggestive**: runs of 8 identical catalogIds under distinct piece ids (Loft) — consistent with copy-paste preserving catalogId.
- **EX-1 · SH3D 7.4 emits `<shelfUnit>`** (absent from the spec's element vocabulary) — a tag-keyed furniture walk drops pieces. Also new: `license`, `widthInPlan`/`depthInPlan`/`heightInPlan`, `widthDepthDeformable` attributes; a `<transformation>` child under doorOrWindow.
- **EX-2 · the current converter aborts on all four real files** (28/18/14/6 errors): **39% of real Rooms are unnamed** (37/95; all 4 Loft Rooms), duplicate Room names are idiomatic across *and within* Floors (Blues: "salle de bain" ×6, 4 on one Floor), diagonals exist. Fine for the family's disciplined drawing; "import anything" is a non-goal, permanently recorded.
- **EX-3 · negative plan coordinates are the norm** (3 of 4 files; Blues to −700 cm). Loft never comes near the origin either. The min-shift origin handles both; no repo fixture exercises either. Phase 0 adds one.
- **EX-4 · `elevationIndex` is 0 on all 13 levels**, even Factory's genuine mezzanine stack. The `(elevation, elevationIndex)` sort is safe; same-elevation semantics (V13) unexercised.
- **EX-5 · root noise to skip**: `property`, `furnitureVisibleProperty`, `environment`, `compass`, cameras, `dimensionLine`, `label`. **Blues has zero `<light>` elements** for 218 pieces (its lamps are plain furniture); Loft has 29. Element tag ≠ Device classification — recognition must key on properties/catalogId.
- **EX-6 · Rooms are not always habitable**: `floorVisible="false"` void outlines exist (Factory, Loft). `name` present on only 58/95 rooms.
- **cutOutShape (V15)**: two dialects — bare SVG path data *and* a complete embedded SVG document with XML prolog + DOCTYPE (three of four files). Only relevant if openings are ever adopted.
- **Doors carry no wall IDREF** — confirmed across 162 doorOrWindow elements (`boundToWall` always false/absent). Geometric association would be required; we defer openings instead.
- **Unexercised by any fixture or example** (purpose-built fixtures needed if ever relied on): `viewable` attribute on levels, negative elevations, same-elevation mezzanines, non-zero arcExtent.

## Plan 06 disposition

`06-device-vocabulary-table.md` is superseded **in part**. Its premises die with this series (closed vocabulary as sole input, devices.yaml as position source, entity-id binding, slug-list docs). Five deliverables are carried forward by name — losing any of them silently was the failure mode of "retire wholesale":

1. **Panel-side vocabulary table** (kind → slug/family/seed) → phase 3.
2. **One shared parser for the hand-maintained file** (now `bindings.yaml`, not devices.yaml) + a home for `connectivity: local|cloud` (SR-16: the spec left it homeless) → phase 2.
3. **The dev-Hub stand-in pipeline** (pure generator core, unified seed table, seed-triplication kill — zero spec analogue; the 812 W / 21.4° / "Idle" literals live in three files today) → retargeted in phase 2, deepened in phase 3.
4. **The togglable seam decision** (keep "answered from the House, never from live state") → phase 3 absorbs `device_traits.dart` per plan 06 §9.
5. **A hermetic binding-drift test** (red in `flutter test`, complementing any future live-Hub validation) → phase 2.

Plan 06's icon non-goal ("no icon column — trigger: never") **stands**, because this series keeps the closed enum: `deviceIcon`'s exhaustive switch remains compiler-policed. (The analysis note that an open vocabulary would invert this is recorded in phase 3 as the trigger.)

## ADRs

- **ADR-0004** stays: y-south, rectilinear, tiling, stdlib converter, generated-vs-hand two-lifecycle split, name-slug Room ids — all still binding.
- **ADR-0005** (new, drafted in phase 1): Devices are authored in the drawing; supersedes exactly one ADR-0004 clause — the devices-as-furniture-markers rejection — and records why its two objections no longer hold (typed `<property>` metadata, verified by phase 0; keys+bindings split ownership so regeneration owns no hand data).
