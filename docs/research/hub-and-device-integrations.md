# Hub & Device Integration Research: Headless Hub Behind a Custom Dollhouse Touch UI

Researched 2026-07-30. Synthesized from four research fragments; all claims verified against primary sources (GitHub API, official docs, vendor pages) on that date unless flagged **UNVERIFIED**.

**Context:** always-on AMD Ryzen mini PC (32 GB RAM) hosting the hub 24/7 headless behind a custom dollhouse-style touch UI (Flutter or web). User prefers Java. Reliability first; existing cloud devices accepted as-is; **new purchases must be local-first**. US installation.

---

## 1. Executive Summary

**Recommendation: Home Assistant (HA), deployed as HA Container on plain Linux, with the custom UI speaking HA's WebSocket API.** openHAB is the credible Java runner-up but strands or degrades roughly half of this specific device fleet (Ecobee, Wyze control, Whisker, Petlibro, LG, Emporia). Details in section 5.

Two calendar items regardless of hub choice:

- **October 2026:** Samsung begins phasing out free SmartThings API access ($4.99/mo "Personal Plan") — affects the oven integration on every platform ([HA docs warning](https://www.home-assistant.io/integrations/smartthings/), [SmartThings blog](https://blog.smartthings.com/smartthings-updates/a-new-enhanced-smartthings-api-experience/)).
- **HA 2026.8:** implicit Wake-on-LAN removal for `samsungtv` — define explicit `turn_on`/WOL actions per TV before upgrading past it ([core issue #166226](https://github.com/home-assistant/core/issues/166226)).

## 2. Platform Comparison

Four platforms were evaluated as headless backends: Home Assistant, openHAB, ioBroker, OpenRemote. Ranking for this use case: **HA > openHAB > ioBroker > OpenRemote**.

### Home Assistant

- **Health:** 2026.7 released 2026-07-01, strict monthly cadence with weekly patch releases ([release blog](https://www.home-assistant.io/blog/2026/07/01/release-20267/), [releases](https://github.com/home-assistant/core/releases)). ~89.6k stars, ~38.2k forks, last push 2026-07-30 — the most active project in this space by an order of magnitude ([repo](https://github.com/home-assistant/core)). Apache-2.0, Python.
- **Integrations:** 1000+ built-in integrations, 3000+ supported devices; 4–17 new integrations per monthly release over the past year ([integrations index](https://www.home-assistant.io/integrations/)). Matter server rewritten on matter.js in 2026.7 — Matter 1.5.1, Thread network visualization — the most aggressively developed Matter stack of the four ([2026.7 blog](https://www.home-assistant.io/blog/2026/07/01/release-20267/), [coverage](https://www.techtimes.com/articles/319307/20260629/home-assistant-20267-arrives-july-1-intent-based-automations-matter-server-overhaul.htm)). Zigbee via ZHA or Zigbee2MQTT; Z-Wave via Z-Wave JS ([ZHA](https://www.home-assistant.io/integrations/zha/), [Z-Wave JS](https://www.home-assistant.io/integrations/zwave_js/)).
- **Headless/custom-frontend API — the decisive strength:** the **WebSocket API is the exact API the official frontend uses**, so it is exercised by millions of installs daily and cannot rot: full auth handshake, filtered event subscriptions, trigger subscriptions, service calls, state fetch ([WebSocket API docs](https://developers.home-assistant.io/docs/api/websocket/)). REST API exists but is frozen — "superseded by the WebSocket API" ([architecture discussion #1074](https://github.com/home-assistant/architecture/discussions/1074)). Auth: OAuth2 plus **long-lived access tokens valid 10 years** — ideal for a wall panel ([auth docs](https://developers.home-assistant.io/docs/auth_api/)).
- **Client libraries:** official, maintained [home-assistant-js-websocket](https://github.com/home-assistant/home-assistant-js-websocket) (used by the HA frontend itself) — the best client-library story of any platform here. Dart/Flutter is third-party only ([`home_assistant`](https://pub.dev/packages/home_assistant) v2.0.0, 2025-08-11, REST-oriented); the WS protocol is simple JSON-over-WebSocket, so a hand-rolled Dart client is a small task, but budget for writing it. Python: [HomeAssistant-API](https://pypi.org/project/HomeAssistant-API/).
- **Headless/hosting:** no official "disable frontend" switch, but the frontend is a passive web server a custom panel simply ignores (*characterization — UNVERIFIED as an official headless-mode doc; none exists*). On this machine the realistic layout is plain Linux + **HA Container** (Docker) + Zigbee2MQTT / Z-Wave JS UI / matter-server as sibling containers + kiosk UI on the console; HA Container drops the add-on store, sibling containers replace it (*analysis, not a sourced claim*). Generic x86-64 requirements are trivial for this PC ([install docs](https://www.home-assistant.io/installation/generic-x86-64/)).

### openHAB

- **Health:** 5.2.0 released 2026-07-05; two feature releases per year plus patch releases and a 4.3.x maintenance line — a slow-and-stable cadence that suits a reliability-first appliance ([release blog](https://www.openhab.org/blog/2026-07-05-openhab-5-2-release), [distro releases](https://github.com/openhab/openhab-distro/releases)). ~1.1k stars core / ~2.1k addons, last push 2026-07-30 ([openhab-core](https://github.com/openhab/openhab-core), [openhab-addons](https://github.com/openhab/openhab-addons)). **EPL-2.0, Java (requires Java 21)** ([install docs](https://www.openhab.org/docs/installation/)).
- **Integrations:** surpassed 500 add-ons with 5.2 (19 new bindings in that release) ([5.2 blog](https://www.openhab.org/blog/2026-07-05-openhab-5-2-release)). Official Matter binding actively improved in 5.2 (OTA served by openHAB, Thread visualization) — second-best Matter story after HA. Zigbee: native binding or Zigbee2MQTT via MQTT binding (community favors Z2M for device coverage: [thread](https://community.openhab.org/t/zigbee-binding-or-zigbee2mqtt/135292)). 5.2 also ships an MCP server for AI agents ([5.2 blog](https://www.openhab.org/blog/2026-07-05-openhab-5-2-release)).
- **Headless/custom-frontend API:** REST API with full CRUD + **Server-Sent Events** (`/rest/events`) for push, API tokens for auth, interactive API Explorer ([REST docs](https://www.openhab.org/docs/configuration/restdocs.html), [SSE confirmation](https://community.openhab.org/t/solved-rest-api-server-side-events-documentation/74723)). Genuinely headless — the core is an OSGi/Karaf server; Main UI is an optional add-on.
- **Client libraries — the weak spot:** no maintained external JS client (npm `openhab` is the internal rules-scripting library; `@ds82/openhab` is a stale beta), **zero Dart/Flutter packages**; Python has community [python-openhab-rest-client](https://pypi.org/project/python-openhab-rest-client/). Practical impact: you write ~200 lines of REST+SSE client yourself. SSE is one-directional (commands go over REST) — architecturally fine, less elegant than HA's single WS channel.

### ioBroker

- js-controller 7.1.2 stable; MIT, TypeScript/Node.js; ~294 stars (ecosystem spread across hundreds of adapter repos), last push 2026-07-26 ([repo](https://github.com/ioBroker/ioBroker.js-controller)). "1000+" adapters commonly cited — **UNVERIFIED** (no authoritative total published). Matter adapter is in the stable repo (Matter 1.4.2, controller + bridge) ([repo](https://github.com/ioBroker/ioBroker.matter)).
- API: pure-WebSocket adapter [`iobroker.ws`](https://www.npmjs.com/package/iobroker.ws) plus an **official TypeScript client** [`@iobroker/socket-client`](https://www.npmjs.com/package/@iobroker/socket-client); REST via [`iobroker.rest-api`](https://github.com/ioBroker/ioBroker.rest-api) (Swagger, OAuth2). No Dart packages.
- Why it ranks third: docs/community heavily German-centric, ioBroker-idiosyncratic API semantics (objects/states trees), thinner documentation; historically LAN deployments default to no auth until configured (*common knowledge — UNVERIFIED against current defaults*). Ecosystem depth well below HA/openHAB, and nothing notable surfaced for this device fleet.

### OpenRemote

- Java, genuinely headless-first, textbook OAuth2(Keycloak)/REST/WebSocket/MQTT APIs ([Manager APIs docs](https://docs.openremote.io/docs/user-guide/manager-apis/)); very active (1.28.1 published 2026-07-30). **AGPL-3.0** — the only copyleft license of the four ([LICENSE](https://raw.githubusercontent.com/openremote/openremote/master/LICENSE.txt)).
- **Wrong category despite the appealing architecture:** it is an IoT *asset-management* platform (smart cities, energy) — **no Zigbee, no Matter, no Thread** ([agent overview](https://docs.openremote.io/docs/user-guide/agents-protocols/overview)), no consumer-device catalog. Every device here would become a manual MQTT/HTTP integration project. JS/TS client only, no Dart.

### Other contenders (dismissed)

Verified against primary sources 2026-07-30:

- **Domoticz** — alive and improving: stable 2026.2 released 2026-05-31 with native Matter support and a new dashboard ([domoticz.com/2026.2](https://www.domoticz.com/2026.2/)); GPL-3.0, C++ (Lua/Python scripting), ~3.8k stars ([repo](https://github.com/domoticz/domoticz)). But its integration model (C++ hardware plugins + Python plugins, "150+ hardware" catalog) has essentially nothing for this device fleet (no Ring/Wyze/Ecobee/ThinQ/Whisker/Petlibro paths), and its JSON API is dated. Not competitive here.
- **Gladys Assistant** — actively maintained (Apache-2.0, Node.js, ~3.1k stars, active PR flow: [repo](https://github.com/GladysAssistant/Gladys)) but its integration catalog is dozens, not hundreds — nothing for this fleet beyond generic MQTT/Zigbee2MQTT.
- **Homey** — the hub platform is a commercial Athom B.V. product; the backend/firmware is not open source (only the app SDK is), so it is out of scope for an open-source-hub comparison (*characterization from product positioning; not further researched this session*).
- **FHEM** (Perl, German-centric) and **Jeedom** (PHP, French/commercial) remain niche per 2026 roundups ([Geekflare roundup](https://geekflare.com/consumer-tech/open-source-home-automation-tools/)). No serious new open-source platform emerged in 2025–2026. **UNVERIFIED:** exhaustiveness of this sweep.

**Cross-cutting note:** Zigbee2MQTT and Z-Wave JS UI run as standalone daemons speaking MQTT/WebSocket, so the Zigbee/Z-Wave radio layer can be decoupled from the hub choice entirely — HA, openHAB, and ioBroker can all consume them ([openHAB community precedent](https://community.openhab.org/t/zigbee-binding-or-zigbee2mqtt/135292)).

## 3. Devices

### 3.1 Ring Video Doorbell — ☁️ cloud, permanently

- **HA:** official core integration, IoT class Cloud Polling (60 s polling + push events over Google FCM). **There is no local API for Ring devices at all** — a Ring platform limitation, not an integration gap ([HA docs](https://www.home-assistant.io/integrations/ring/)). Exposes per camera `live_view` and `last_recording` entities (last recording needs Ring Protect), ding/motion/intercom events, battery/Wi-Fi sensors, motion-detection and chime switches, lights, siren, intercom unlock, volume. Two-way audio not supported. Quality scale: Bronze.
- Live view is WebRTC negotiated through Ring's cloud, merged in [core PR #127579](https://github.com/home-assistant/core/pull/127579) (shipped HA 2024.12) — on-demand viewing, **not** a 24/7 RTSP stream.
- **Known 2026 issue:** open [core issue #177014](https://github.com/home-assistant/core/issues/177014) (2026-07-21) — WebRTC live-view sessions can remain active after the frontend closes, **suppressing subsequent doorbell/motion events** (Ring cameras don't send alerts while streaming). A Dec 2025 SDP-error report ([#158118](https://github.com/home-assistant/core/issues/158118)) was closed "not planned". 2026.7-beta streaming-breakage reports circulate on third-party blogs — **UNVERIFIED** (only source is a low-trust SEO site, https://quvii.com/learn/ring-plugin-not-streaming-home-assistant-2026-7-fix/).
- **ring-mqtt** ([tsightler/ring-mqtt](https://github.com/tsightler/ring-mqtt)): actively maintained (v5.9.3, 2026-03-09); bridges Ring cloud to local MQTT + RTSP gateway (bundled go2rtc). Survived Ring's FCM migration ([changelog](https://github.com/tsightler/ring-mqtt/blob/main/docs/CHANGELOG.md)) but is single-maintainer. **Maintainer's own hard limitation:** all streaming still transits Ring's cloud; 24/7 streaming and NVR/Frigate use are explicitly unsupported — drains batteries, overheats devices, suppresses events (README "IMPORTANT NOTE").
- **openHAB:** official binding exists but is **marked experimental** — events, battery, snapshots, recorded-video download (Ring Protect required), and **"currently does not support live video streaming"**; 2FA setup only via Main UI ([binding docs](https://www.openhab.org/addons/bindings/ring/)). Years of auth-breakage churn on older marketplace versions ([community thread](https://community.openhab.org/t/ring-doorbell/4477)).
- **Recommended path:** HA core Ring for events/entities + dashboard live view; add ring-mqtt only if RTSP/MQTT fan-out is needed. Do not plan on Ring-in-Frigate or 24/7 recording — architecturally impossible without Ring cloud. Drive automations from doorbell *events*, not video. On openHAB you lose live view entirely.

### 3.2 Wyze cameras (incl. floodlight) — ✅ local possible for v3-class, 🧩 bridge for the rest

- **Official RTSP is back (the big 2025–2026 development):** Wyze shipped RTSP/RTSPS beta for **Cam v3 and Cam Pan v3** in Oct–Nov 2025 ([beta page](https://wyze-beta.s3.us-west-2.amazonaws.com/rtsp.html)), then promoted it to **production firmware on 2026-02-02** (v3 4.36.16.5654, Pan v3 4.50.16.5654; app ≥3.9; enable in Advanced Settings; standard RTSP or encrypted RTSPS, no subscription mentioned) ([beta thread](https://forums.wyze.com/t/rtsp-beta-release-for-v3-and-pan-v3/338245), [firmware announcement](https://forums.wyze.com/t/wyze-firmware-updates-2-2-2026/340669)). **No RTSP for v4** — a firmware change actually *broke* bridge RTSP on v4 ([forum thread](https://forums.wyze.com/t/wyze-cam-v4-rtsp-removed-5-cameras-now-useless-for-their-intended-purpose/341508)).
- **Floodlight models** (per upstream bridge README support matrix, https://github.com/mrlt8/docker-wyze-bridge): Wyze Cam Floodlight (WYZE_CAKP2JFUS — a Cam v3 on a floodlight mount) full support; Floodlight V2 (HL_CFL2) full; **Floodlight Pro (LD_CFP) limited/experimental**. **UNVERIFIED:** whether the Feb-2026 official RTSP firmware applies to the v3-based Floodlight bundle — plausible (same camera) but not explicitly listed in Wyze's release thread.
- **docker-wyze-bridge:** upstream mrlt8 repo is **dormant** (last release v2.10.3, 2024-09-13). Wyze's early-2025 firmware auth change broke all forks unless firmware is pinned ([issue #1517](https://github.com/mrlt8/docker-wyze-bridge/issues/1517) — lists last-known-good firmware per model; `network_mode: host` now mandatory). **The maintained successor is the [IDisposable fork](https://github.com/IDisposable/docker-wyze-bridge)** — v4.5.0 (2026-07-02) adds runtime TUTK→WebRTC auto-fallback for cameras Wyze crippled via firmware (targets Cam v4) ([releases](https://github.com/IDisposable/docker-wyze-bridge/releases), [HA community adoption](https://community.home-assistant.io/t/picked-up-docker-wyze-bridge-project-updates/873251), [Docker image](https://hub.docker.com/r/idisposablegithub365/wyze-bridge)). Auth is against Wyze cloud via personal **API Key + Key ID** ([console](https://developer-api-console.wyze.com/#/apikey/view), [bridge auth docs](https://github.com/mrlt8/docker-wyze-bridge/wiki/Authentication)); streams are pulled locally but cameras need internet for init.
- **Device control in HA:** no core integration; HACS [SecKatie/ha-wyzeapi](https://github.com/SecKatie/ha-wyzeapi) is active (last push 2026-07-16, 984 stars) — bulbs/plugs/locks/camera on-off + events via Wyze cloud, **not** video.
- **Frigate:** bridge→Frigate works but has a documented flakiness history ([#175](https://github.com/mrlt8/docker-wyze-bridge/issues/175), [#1017](https://github.com/mrlt8/docker-wyze-bridge/issues/1017), [discussion #939](https://github.com/mrlt8/docker-wyze-bridge/discussions/939)). Best 2026 Frigate path: **official RTSP firmware straight into Frigate/go2rtc — no bridge, no cloud in the video path**.
- **De-cloud firmware:** [wz_mini_hacks](https://github.com/gtxaspec/wz_mini_hacks) is no longer in active development; its README recommends **Thingino** open-source firmware instead (more feature-complete, real flash, harder to uninstall). Mostly obsolete for v3/Pan v3 now that official RTSP exists.
- **openHAB:** **no Wyze binding exists**; community path is RTSP + the [`ipcamera` binding](https://community.openhab.org/t/ipcamera-new-ip-camera-binding/42771). Wyze plug/bulb control has no OH path at all.
- **Recommended path:** put v3/Pan v3 units (incl. v3-based floodlight) on the Feb-2026 RTSP production firmware → Frigate/go2rtc, fully local video. Everything else via the IDisposable bridge fork with an API key — pin camera firmware and disable auto-updates. Treat Wyze cloud/auth churn as an ongoing reliability risk (their 2025 firmware change broke every bridge for months).

### 3.3 Ecobee thermostat — ☁️ core + ✅ local HomeKit on HA; ❌ stranded on openHAB

- **Developer API closed:** Ecobee halted new developer API keys on 2024-03-28; existing keys keep working; no sign of reopening as of mid-2026 ([core issue #131789](https://github.com/home-assistant/core/issues/131789), [HA community](https://community.home-assistant.io/t/ecobee-no-longer-allows-api-keys/805553), [ecobee developers](https://www.ecobee.com/en-us/developers/), [beestat discussion](https://community.beestat.io/t/ecobee-api-beestat/1207)).
- **HA core `ecobee`** (Cloud Polling): climate with presets/holds/aux heat, humidifier, ventilator, remote-sensor temperature/occupancy, weather, vacations/climate-hold actions ([HA docs](https://www.home-assistant.io/integrations/ecobee/)). **Key 2026 change: since HA 2026.3 no developer API key is needed** — authenticate with ecobee username/password (TOTP MFA supported), which neutralizes the 2024 dev-program shutdown for HA users ([HA docs](https://www.home-assistant.io/integrations/ecobee/), [background](https://community.home-assistant.io/t/ecobee-configuration-without-developer-access-or-api-key/724627)).
- **Local option (HA only):** Ecobee thermostats are HomeKit-certified, so HA's `homekit_controller` gives **fully local LAN control** — mode/setpoints, fan, humidity, remote SmartSensor data. Missing vs. cloud: schedules, vacations, ventilator/advanced settings, weather. Pairing can be finicky (mDNS; pairing mode; host networking if containerized) ([user thread](https://community.home-assistant.io/t/ecobee-and-homekit-device-integration/725325)). Cloud + HomeKit can run **simultaneously** — cloud for features, HomeKit for local resilience ([same thread](https://community.home-assistant.io/t/ecobee-and-homekit-device-integration/725325), [setup write-up](https://jpk.io/home-automation/ecobee-home-assistant-setup/)).
- **No native Matter:** the Smart Thermostat Premium is HomeKit-only, no Matter ([review](https://www.gearbrain.com/ecobee-premium-smart-thermostat-review-2677164902.html)) — **UNVERIFIED** whether any 2026 firmware adds Matter; no ecobee support article found announcing it.
- **openHAB:** the official ecobee binding still requires a developer API key via the now-closed portal — **effectively unusable for anyone without a pre-2024 key** ([binding docs](https://www.openhab.org/addons/bindings/ecobee/)). openHAB's HomeKit add-on only *exposes* items to Apple Home; it cannot consume HomeKit accessories ([add-on docs](https://www.openhab.org/addons/integrations/homekit/)) — so **openHAB has no local path either**. This is a significant HA-over-OH argument.
- **Recommended path:** HA core ecobee (username/password auth) for full features + HomeKit Device pairing for local control that survives internet/Ecobee-cloud outages.

### 3.4 Emporia Vue 3 — 🧩☁️ stock, ✅🔧 fully local via ESPHome reflash

- **Official position:** no public API, no local API/network interface on any Vue device — all data flows through Emporia's cloud; community projects acknowledged but unsupported ([Emporia help article](https://help.emporiaenergy.com/en/articles/13297125-developer-access-future-integrations)).
- **HA, stock firmware:** HACS custom repo [magico13/ha-emporia-vue](https://github.com/magico13/ha-emporia-vue) (not in HACS default store) — Emporia app credentials, polls the cloud via PyEmVue, 1-minute per-circuit data. Actively maintained (last push 2026-06-28, 735 stars); works with Vue 3 ([confirmation thread](https://community.home-assistant.io/t/emporia-vue-3/915845), [install thread](https://community.home-assistant.io/t/hacs-and-emporia-vue-integration-problem-with-installation/324112)).
- **ESPHome reflash — documented for Vue 3 specifically:** the [emporia-vue-local](https://github.com/emporia-vue-local/esphome) project (maintained ESPHome fork carrying the `emporia_vue` component, which is *not* in upstream ESPHome) has a dedicated **`vue3` branch** and activity through 2026-04-19. Official flashing docs include Vue 3 hardware prep and stock-firmware backup ([flashing tutorial](https://emporia-vue-local.github.io/docs/tutorial/flashing/)); origin discussion ([#264](https://github.com/emporia-vue-local/esphome/discussions/264)), flash jig ([#305](https://github.com/emporia-vue-local/esphome/discussions/305)); independent walk-throughs: [digiblur](https://digiblur.com/2024/03/14/emporia-vue-gen3-esp32-esphome-home-assistant/) (its [companion repo](https://github.com/digiblur/esphome-vue3) is stale — use the `vue3` branch as the living source), [fuzznotes](https://fuzznotes.com/posts/flash-emporia-vue-3-with-esphome/), [dracoli](https://dracoli.ch/posts/vue3-esphome-ha/).
- **Caveats:** open the case, wired UART flash (GPIO0 grounded at power-on), Vue 3 needs different I²C config/calibration than Vue 2, power-hungry during flashing (brownout reports — strong 3.3 V supply), **back up stock firmware first** (flashing removes Emporia app/cloud until restored), occasional bricking reports ([#349](https://github.com/emporia-vue-local/esphome/discussions/349)). After flashing: 5-second local updates into HA's ESPHome integration and Energy dashboard — zero cloud.
- **openHAB:** no binding; an ESPHome-flashed Vue 3 can reach it via MQTT or the actively maintained community [ESPHome native-API binding](https://github.com/seime/openhab-esphome) (last push 2026-07-30) ([community thread](https://community.openhab.org/t/emporia-vue-gen2-with-oh/142522)).
- **Recommended path:** reflash with ESPHome (emporia-vue-local `vue3` branch, follow the official docs, back up stock firmware) for fully local 5 s data. If you won't open the case, the magico13 HACS cloud integration is maintained and functional at 1-minute granularity.

## 4. New Outlets & Switches — Buying Recommendation (US, local-first)

**Primary protocol: Zigbee, run through Zigbee2MQTT, with an SMLIGHT SLZB-06 (PoE/Ethernet) coordinator** (or Sonoff ZBDongle-E + USB extension cable if you prefer USB).

### Why Zigbee + Z2M

1. **Local-first:** Zigbee devices have no cloud, no vendor app, no firmware phoning home.
2. **Custom-hub-friendliness is the killer argument:** Zigbee2MQTT publishes every device as plain MQTT topics with JSON payloads. HA consumes them via MQTT discovery, openHAB via its MQTT binding, and a custom Java dollhouse panel via any Java MQTT client (Paho/HiveMQ) — *the same devices serve all three without re-pairing*. The device layer becomes independent of the hub-software decision ([Z2M](https://www.zigbee2mqtt.io/guide/adapters/), [openHAB MQTT precedent](https://community.openhab.org/t/goodby-myq-say-hello-to-ratgdo-garage-door-control/153832)).
3. **Reliability:** dedicated 2.4 GHz mesh where every mains-powered outlet/switch is a repeater; no dependence on your Wi-Fi AP. Matter-over-Thread in 2026 still has border-router and fragmentation pain that conflicts with a "reliable, not exploratory" priority ([Matter 2026 status review](https://matter-smarthome.de/en/development/the-matter-standard-in-2026-a-status-review/), [Thread critique](https://matter-smarthome.de/en/development/is-the-thread-protocol-matters-achilles-heel/)).
4. An Ethernet coordinator keeps the radio central in the house and decoupled from the always-on PC's USB stack and any future virtualization ([zigbeehubs SLZB-06](https://zigbeehubs.com/blog/slzb-06/)).

### Coordinator

- **SMLIGHT SLZB-06 (CC2652P, Ethernet/PoE/USB)** — the pick: network-attached (place centrally, survives OS rebuilds/VM moves, no USB passthrough); TI CC2652P is the most battle-tested Z2M platform; the EFR32-based SLZB-06M/-07 are flagged experimental in Z2M per SMLIGHT's own docs ([SLZB-06](https://smlight.tech/product/slzb-06), [SLZB-06M](https://smlight.tech/product/slzb-06m), [models overview](https://smlight.tech/manual/slzb-06/guide/slzb-models-overview/)). Use **Ethernet, not its Wi-Fi mode** — Z2M explicitly warns serial-over-WiFi is failure-prone ([Z2M adapters guide](https://www.zigbee2mqtt.io/guide/adapters/)). Flag: SMLIGHT's "experimental" label for its EFR32 models may lag Z2M's current ember-driver status.
- **Sonoff ZBDongle-E (EFR32MG21, USB)** — budget USB pick; may need a firmware update for current Z2M; use a USB extension cable (USB3 ports are notorious 2.4 GHz interferers — long-standing community guidance, **UNVERIFIED** against a primary source this session) ([SmartHomeScene guide](https://smarthomescene.com/top-picks/best-zigbee-coordinators-for-home-assistant/), [zigbeehubs review](https://zigbeehubs.com/sonoff-zbdongle-e/)).
- **Home Assistant Connect ZBT-2** ($49, Nov 2025, Silicon Labs MG24) — nicest new hardware; Zigbee **or** Thread (not both at once); buy instead if you want a future Thread-radio option in the drawer ([HA blog](https://www.home-assistant.io/blog/2025/11/19/home-assistant-connect-zbt-2/), [CNX Software](https://www.cnx-software.com/2025/11/20/home-assistant-connect-zbt-2-zigbee-thread-usb-adapter/)).
- If Z-Wave instead: **Zooz ZST39 LR** 800-series USB stick + Z-Wave JS UI in Docker (about half the price of HA's ZWA-2, same 800-series silicon) ([Zooz](https://www.getzooz.com/zooz-zst39-z-wave-long-range-usb-stick/), [HA Z-Wave adapters doc](https://www.home-assistant.io/docs/z-wave/controllers/), [comparison](https://community.home-assistant.io/t/home-assistant-connect-zwa-2-vs-zooz-zst39/962971)). Note: openHAB's new official `zwavejs` binding consumes the same Z-Wave JS UI websocket, but **Long Range inclusion is not supported** in it ([binding docs](https://www.openhab.org/addons/bindings/zwavejs/), [release thread](https://community.openhab.org/t/new-z-wave-js-binding-released/164943)).

1. **Inovelli Blue Series 2-1 (VZM31-SN) wall switches/dimmers** — the best Zigbee wall switch made: on/off or dimmer in one device, neutral or no-neutral, LED notification bar, Zigbee direct binding to smart bulbs; firmware actively updated (v3.07, March 2026); fully supported in Z2M/ZHA ([Inovelli](https://inovelli.com/products/zigbee-matter-blue-series-smart-2-1-on-off-dimmer-switch), [firmware changelog](https://community.inovelli.com/t/blue-series-2-1-firmware-changelog-vzm31-sn/12326), [Z2M compatibility](https://zigbee.blakadder.com/Inovelli_VZM31-SN.html)).

Great default plug-in outlet ([product](https://www.thirdreality.com/products/smart-plug-gen2-power-metering), [manual](https://3reality.com/wp-content/uploads/2024/09/Smart-Plug-Gen2_UM_20240925.88.pdf)).
3. **Athom pre-flashed ESPHome plugs** for special cases — fully-owned firmware: US V2 16 A power-monitoring plug, ESP32-C3 variant, and the **no-relay monitoring-only plug** (cannot cut power — ideal for metering the hub PC / networking gear itself) ([US V2](https://www.athom.tech/blank-1/us-v2-plug-for-esphome), [ESP32-C3](https://www.athom.tech/blank-1/esp32-c3-us-plug-for-esphome), [no-relay](https://www.athom.tech/blank-1/no-relay-power-monitoring-us-plug-for-esphome)).
4. *(Optional)* **Lutron Caséta + Smart Bridge** for a handful of mission-critical lighting circuits: unmatched reliability on its own Clear Connect RF band, local LEAP support in both HA core and openHAB's stock binding, premium prices ([HA docs](https://www.home-assistant.io/integrations/lutron_caseta/), [openHAB binding](https://www.openhab.org/addons/bindings/lutron/)).
5. *(Optional)* **Shelly Gen3/Gen4** behind-the-wall relays to keep existing dumb switches: fully local Wi-Fi with native MQTT (custom-hub-friendly), HA core + openHAB stock binding; Gen4 units can alternatively join the Zigbee mesh and add Matter-over-WiFi ([openHAB Shelly binding](https://www.openhab.org/addons/bindings/shelly/), [Gen4 overview](https://www.reichelt.com/magazin/en/news-en/one-module-all-the-possibilities-shelly-gen4-redefines-smart-home-integration/), [Gen4 Zigbee in HA](https://community.home-assistant.io/t/shelly-gen4-with-zigbee/866428), [Gen4 US plug](https://9to5mac.com/2026/03/13/homekit-weekly-shelly-gen4-plug-brings-wi-fi-6-matter-and-thread-to-a-single-outlet/)).

**What not to buy now:** Matter-over-Thread outlets as the mainline (border-router + fabric complexity vs. the reliability goal; revisit in a year — the openHAB Matter binding and HA Matter server are improving fast ([openHAB Matter thread](https://community.openhab.org/t/matter-binding/164601))); cloud-dependent Wi-Fi plugs (Wyze, Govee, etc.). Also noted: TP-Link Kasa/Tapo are local-capable and cheap ([HA docs](https://www.home-assistant.io/integrations/tplink/), [python-kasa](https://github.com/python-kasa/python-kasa)) but newer Tapo firmware needs TP-Link cloud credentials once for the local auth handshake, and openHAB Tapo support is via a community "TapoControl" binding — **UNVERIFIED this session**.

## 5. Recommendation

### The hub: Home Assistant (Container deployment)

**Choose Home Assistant.** The reasoning, in order of weight:

1. **Device coverage is decisive for this exact fleet.** The matrix in section 1 is lopsided: openHAB has *no path at all* for Ecobee (binding gated on a closed developer program, no HomeKit-consumer capability), Whisker, Petlibro (both feeders), or Wyze device control, and its LG ThinQ community binding is broken pending a rewrite. HA covers every device on its best-known 2026 path, including two local upgrades openHAB cannot match: Ecobee via HomeKit controller and Ring live view.
2. **For a custom-UI-on-top architecture, the API is the product** — and HA's WebSocket API is the only one in the field that is continuously battle-tested by the platform's own frontend at massive scale ([WS docs](https://developers.home-assistant.io/docs/api/websocket/)). Add OAuth2 plus 10-year long-lived tokens for the wall panel, and the official maintained `home-assistant-js-websocket` client.
3. **Ecosystem trajectory:** best Matter/Thread stack (matter.js, Matter 1.5.1), ZHA/Z-Wave JS/Z2M coverage, 1000+ integrations, monthly releases, ~89.6k-star project health.

**Costs to accept:** Python under the hood (irrelevant — you consume the API, never touch the backend, so the Java preference is expressed in the panel and any sidecar services instead); monthly release cadence (pin versions and update on your own schedule; breaking changes are documented per release); a DIY Dart WS client if the panel is Flutter — or use the official JS library and build the panel as a web kiosk.

**openHAB remains the pick only if** the Java preference is meant to include hacking on the hub's internals: EPL-2.0 Java, calm twice-yearly releases, adequate REST+SSE, 500+ add-ons, a genuinely good Matter binding. But for this device fleet it strands too much, and you'd write your own REST/SSE client anyway (no maintained external client libraries). ioBroker and OpenRemote are not competitive here (section 2).

### Deployment layout on the mini PC

Plain Linux + Docker (*analysis from the platform fragment, not a sourced claim*):

- **HA Container** (headless; its built-in frontend is passive and ignored by the panel)
- **Zigbee2MQTT** + MQTT broker (Mosquitto) → SMLIGHT SLZB-06 over Ethernet
- **Frigate / go2rtc** for Wyze v3/Pan v3 RTSP streams
- **IDisposable wyze-bridge** for non-RTSP Wyze models
- Optional: **ring-mqtt**, **Z-Wave JS UI**, **matter-server** as needs arise
- Chromium/Flutter kiosk on the console for the dollhouse UI

### What the custom UI talks to

- **Primary channel: HA's WebSocket API** with a long-lived access token — entity states, filtered event subscriptions, and service calls for every integrated device (Ring events, Ecobee, oven state + Stop, TVs, Whisker, Petlibro, LG laundry, ratgdo garage, Tesla Wall Connector, Zigbee outlets/switches). If the panel is web-tech, use [`home-assistant-js-websocket`](https://github.com/home-assistant/home-assistant-js-websocket); if Flutter, budget a small hand-rolled JSON-over-WebSocket client.
- **Video, direct (bypassing HA):** Wyze v3/Pan v3 RTSP via Frigate/go2rtc; other Wyze models via the wyze-bridge's WebRTC/RTSP outputs. Ring live view via HA's WebRTC camera entity, on demand only — and mind [issue #177014](https://github.com/home-assistant/core/issues/177014) (open streams suppress doorbell events).
- **Optionally direct MQTT** for latency-critical or hub-independent widgets: Zigbee2MQTT topics and ratgdo (if flashed with MQTT firmware) speak plain MQTT that a Java client (Paho/HiveMQ) can consume alongside HA — the device layer stays portable if the hub decision is ever revisited.
- **Not on the panel (no integration path):** myQ camera (app-only; add a local RTSP camera if garage video matters), LR5 Pro camera (Whisker app or custom pylitterbot code), Petlibro Granary camera (WIP upstream).
