# Why ffmpeg destroys the doorbell's inbound audio — and why we still cannot say

**Status:** the *observation* is settled and load-bearing; the *explanation* is
not. This note exists so the reproduction survives the deletion of
`hub/dev/ring-twoway-lab/`, and so nobody files an upstream bug that the
maintainers can immediately refute.

Written 2026-08-08, from the measurements in that lab's `RESULTS.md` §B4h/§B5
plus a controlled negative result taken the same day.

---

## 1. The observation — solid, measured twice, on two OS releases

The same `rtsp://…/ring` stream, consumed **simultaneously** by two clients
during ~50 s of real speech at the front door:

| Release / clients | ffmpeg: samples with \|v\| > 1.0 | GStreamer | ffmpeg peak | GStreamer peak |
|---|---|---|---|---|
| Ubuntu 26.04 — GStreamer 1.28.2 / ffmpeg 8.0 | **36 642** | **0** | +34.9 dBFS | 0.0 dBFS |
| Ubuntu 24.04 — GStreamer 1.24.2 / ffmpeg 6.1.1 | **44 404** | **0** | +11.2 dBFS | 0.0 dBFS |

Spectral variance collapses with it: 56.5 dB (ffmpeg) → 15.4 dB (GStreamer), and
the owner confirmed by ear — *"the playback is good, no any extra pitch sounds."*
An `rms` **above full scale** on the ffmpeg side is the giveaway that this is not
audio at all.

**The operational rule that follows is unaffected by anything below:**

> 🔴 Consume the doorbell's inbound audio with **GStreamer**. Never with ffmpeg.
> Outbound is a different code path (ffmpeg *packetises* there) and measures
> clean — 3 stray samples, ~39 dB SNR — so outbound needs no change.

That rule rests on the differential above, not on any theory of the cause.

## 2. The explanation everyone (including this repo) settled on

`RESULTS.md` §B4h concluded, and ADR-0011 and this repo's package comments then
repeated:

> ffmpeg's RTP Opus **depacketiser** mishandles Ring's unusual ~60 ms Opus frames.

The reasoning was circumstantial but reasonable: Ring's receiver stats show a
**constant 17.5 packets/s** (≈ 57 ms per packet) against Opus's usual 50/s, and
our own outbound `mic` stream — ffmpeg-encoded at the default 20 ms framing —
never triggers the bug. Frame size was the one variable that lined up.

## 3. 🔴 It does not reproduce. Measured 2026-08-08.

Synthetic Opus/RTP, generated by GStreamer, consumed by **ffmpeg 6.1.1-3ubuntu5
in this devcontainer** — the same build, on the same image, that produced 44 404
bad samples on Ring's stream. Same measurement (`|v| > 1.0` on a 32-bit-float
decode), 15 s per run, both clients fed the identical stream:

| Variant | encode | frame | extra | ffmpeg | GStreamer |
|---|---|---|---|---|---|
| control | stereo | 20 ms | — | **0** | 0 |
| the hypothesis | stereo | **60 ms** | — | **0** | 0 |
| mono coded, `/2` declared (Ring's shape) | mono | 60 ms | — | **0** | 0 |
| + inband FEC (Ring sends `useinbandfec=1`) | mono | 60 ms | `inband-fec=1` | **0** | 0 |
| + FEC and DTX | stereo | 60 ms | `inband-fec=1 dtx=1` | **0** | 0 |
| 40 ms | stereo | 40 ms | — | **0** | 0 |
| restricted low-delay | stereo | 60 ms | `audio-type=restricted-lowdelay` | **0** | 0 |

Peak and RMS agree with GStreamer's to 0.1 dB in every row.

**So "ffmpeg breaks on 60 ms Opus frames" is false as stated.** ffmpeg 6.1.1
depacketises 60 ms Opus RTP correctly, including in the mono-coded /
stereo-declared / FEC configuration Ring negotiates.

### How the reproduction was run

```sh
# receiver SDP — nothing in it is Ring-specific
cat > stream.sdp <<'SDP'
v=0
o=- 0 0 IN IP4 127.0.0.1
s=opus-rtp-repro
c=IN IP4 127.0.0.1
t=0 0
m=audio 5004 RTP/AVP 96
a=rtpmap:96 opus/48000/2
SDP

ffmpeg -nostdin -v error -protocol_whitelist file,udp,rtp -i stream.sdp \
       -c:a pcm_f32le -f wav ffmpeg.wav &
sleep 2
gst-launch-1.0 -q audiotestsrc num-buffers=1500 samplesperbuffer=480 wave=ticks \
    ! audio/x-raw,rate=48000,channels=2 ! audioconvert ! audioresample \
    ! opusenc frame-size=60 bitrate=64000 ! rtpopuspay pt=96 \
    ! udpsink host=127.0.0.1 port=5004 sync=true
```

then the same source into
`udpsrc ! rtpjitterbuffer ! rtpopusdepay ! opusdec ! … ! wavenc`, and both WAVs
counted for samples outside ±1.0. **`-c:a pcm_f32le` matters**: a 16-bit capture
pins everything at 0 dBFS and hides exactly the damage being measured.

## 4. What is therefore still unknown

The corruption is real and it is on our side of Ring's cloud (the Ring app and
go2rtc's own WebRTC page both sound perfect on the identical stream). But the
mechanism is unisolated, and **at least four differences** between the
reproduction above and the real path remain untested:

1. **Transport.** The repro is raw RTP over UDP from an SDP file. The real path
   is **RTSP, TCP-interleaved**, which is the only transport go2rtc's RTSP server
   offers (UDP returns `461 Unsupported transport`).
2. **The producer.** go2rtc is *repackaging* WebRTC RTP into RTSP — not
   generating fresh RTP as `rtpopuspay` does. Sequence numbers, timestamps,
   marker bits and packet boundaries all come from Ring via pion.
3. **Ring's actual packetisation.** 17.5 packets/s is ~57 ms, not 60. Whether
   those are single 60 ms frames, code-3 packets carrying 3 × 20 ms, or something
   irregular has never been looked at — nobody has decoded a TOC byte.
4. **Ring's exact SDP answer** — `a=fmtp:96 useinbandfec=1`, no `minptime`,
   `stereo`/`sprop-stereo` absent (so mono per RFC 7587), `a=sendonly`.

Note also that §B4g measured a `-c:a copy` capture decoding **bit-identically**
to the live path — which proves the frames were already corrupt *as ffmpeg
extracted them from RTSP*, but does not distinguish ffmpeg's RTSP demuxer from
its RTP depacketiser, because both were ffmpeg's.

## 5. Consequences

- **Nothing operational changes.** GStreamer inbound, ffmpeg outbound, no
  post-processing. §1's differential is the evidence for that and it stands.
- **The upstream report is not fileable yet** (the plan's §6 item 6). A bug
  report whose reproduction is "own a Ring doorbell" will be closed, and the one
  concrete claim it would make — 60 ms frames — is now known to be wrong. Filing
  it as it stands would waste a maintainer's time and cost us credibility.
- **ADR-0011 and this repo's package comments overstate the cause.** They are
  amended to say what was measured rather than why.

## 6. What would actually settle it — one short dial, then offline forever

The whole remaining question can be answered without ever touching the doorbell
again, *if* one capture is taken while it is live:

```sh
# inside the go2rtc container, TIME-BOUNDED AT THE FAR END (a killed caller does
# not kill the work — that is how a stray curl held live view for 30 minutes)
timeout 20 ffmpeg -nostdin -v error -rtsp_transport tcp \
    -analyzeduration 10M -probesize 10M -i rtsp://127.0.0.1:8554/ring \
    -vn -c:a copy /tmp/ring-raw.mka          # raw Opus frames, no decode
timeout 20 tcpdump -i lo -s0 -w /tmp/ring-rtsp.pcap 'tcp port 8554'   # if available
```

With those two files, all of this becomes offline analysis with zero Ring
traffic: dump each Opus packet's TOC byte and frame count, compare RTP timestamp
deltas against the frame duration they claim, replay the exact packet sequence
into both depacketisers, and bisect. That is also the material an upstream report
needs — a packet trace and a byte-exact input, not a doorbell.

**It costs one live view of ~20 s.** That is a household device on somebody's
battery, and HA core #177014 means an open stream can suppress a real ding, so it
is the owner's call to make, not an agent's.

## Method notes worth keeping

- **Count samples, do not listen.** Three of the six wrong theories in
  `RESULTS.md` survived a listening test. `|v| > 1.0` on a float decode did not.
- **Capture float.** Every `max_volume: 0.0 dB` in the older notes is a 16-bit
  artefact and should be read as "at or above full scale", not as a true peak.
- **A negative result needs the same rigour as a positive one.** The sweep above
  ran the control (20 ms) through the identical harness precisely so "0 bad
  samples" could not be an artefact of a harness that measures nothing.
