# Devices are authored in the House Plan drawing

ADR-0004 rejected devices-as-furniture-markers because "device metadata doesn't fit a furniture name and regeneration would own hand data." Both objections are now answered and that one clause is superseded — narrowly. Every other ADR-0004 decision stands: meters, one NW origin shared by all Floors, x east y south, rectilinear footprints, Rooms tiling each Floor, Walls first-class, the converter rejecting diagonals and overlaps and never inventing geometry, stdlib-only single script, Room ids slugified from drawn names, and the two-lifecycle split between generated and hand-maintained files.

**Metadata no longer rides the name.** Sweet Home 3D's user-defined `<property>` elements survive a stock open-edit-save round trip: measured in 7.5, 13 of 13 pieces kept theirs, and the application re-serialised them from its own model rather than passing bytes through (measurements in [sweet-home-3d-behaviour.md](../sweet-home-3d-behaviour.md)). So a marker carries `placementKey` and `kind` as typed data, not smuggled inside a name. A generated furniture library, `panel/tool/sh3d_marker_library.py` → `SmartHome.sh3f`, supplies one marker per Device kind with `kind` pre-filled and a `catalogId` of `SmartHome#<kind>`; the family types one Key per Placement and nothing else.

**Regeneration owns no hand data.** The converter emits Placements — Key, kind, name, Room, position — into the generated `house.yaml`. Everything hand-owned (which Hub entity a Key binds to, `local|cloud` connectivity) stays in a file the converter never reads or writes. Re-running the converter therefore remains always-safe, which was the property ADR-0004 was protecting.

**Positions and Room membership are computed, not typed.** Each marker gets the Room whose footprint contains it, with a 0.05 m edge allowance matching the loader's `_pinEps` — pins are deliberately dropped onto walls, and even-odd containment is ambiguous exactly on a boundary. This deletes the House Plan's worst manual step: reading a room id out of a generated file, hovering a spot in Sweet Home 3D, converting cm→m by hand, subtracting the converter's origin-shift line, and typing the result. The evidence that the computation is right is that it reproduced all 33 hand-typed Devices — key, name, kind, room, position — line for line.

**Failures happen at authoring time, in the tool where the fix is.** A marker outside every Room, a duplicate Key, an unknown kind, a marker with no Key, a Placement with no name: each is an error naming the piece as the author sees it in Sweet Home 3D, not a surprise at Panel boot two modules downstream. The loader keeps its own independent gatekeeper checks, so the hand-written-YAML escape hatch gets the same enforcement.

**Keys are free-form.** Any spelling, any separator, any case — Sweet Home 3D constrains none of it and neither do we; only emptiness and collisions are rejected. Imposing a slug pattern would buy consistency the pipeline does not need and cost an error message about punctuation.

**One standing cost, accepted.** The property fields are only editable when Sweet Home 3D is launched with a startup flag declaring them, and that declaration is not saved into the `.sh3d`. The House Plan must therefore be opened via `panel/tool/sh3d.sh`. A normal launch still preserves every value — the fields merely become invisible and uneditable — so the failure mode is confusion, never data loss. There is no way to avoid this short of patching the application: the dialog renders the *Home's* declared property list, which only that flag populates.

**Rejected again, with reasons.** Keys derived from `catalogId` — per-class, so it cannot distinguish two lights, and a per-device registry library would put Hub ids inside the drawing. Orientation and elevation emission — no Dollhouse seam consumes them (pins are circles); when a directional pin ever needs it, the angle is in **radians**, and there must never be a degrees conversion. The Hub's entity ids as identity — they churn, and they are call targets, bound per Key in the hand-maintained file. Tolerance for unnamed or duplicate room names — this pipeline serves one disciplined drawing, not arbitrary imports; measured, 39% of rooms in public example plans are unnamed and would need invented identity. Authored Room or Floor keys — Sweet Home 3D has no property mechanism for rooms or levels at all, so slug-of-name identity stays.
