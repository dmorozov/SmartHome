# House Plan drawn in Sweet Home 3D, converted to YAML the Panel loads

No blueprint of the real house exists (one may be retrieved later, but only as reference material). The House Plan is therefore *drawn*: Sweet Home 3D (free, macOS, one level per Floor, rooms named in-tool, real centimeters) is the authoring tool of record. A stdlib-only Python script, `panel/tool/sh3d_to_yaml.py`, unzips the `.sh3d`, reads its `Home.xml`, and emits geometry; the Panel bundles the YAML as Flutter assets and parses it at startup with the `yaml` package, replacing the hardcoded `demo_house.dart`. Generic SVG export was rejected because it loses the semantics a converter needs (which shapes are rooms, their names, the pixel→meter scale) and pushes those onto hand-maintained conventions; hand-written YAML was rejected only as the primary path (it remains the escape hatch).

Two files with two lifecycles: `house.yaml` (Floors → Rooms → Walls) is **generated and never hand-edited** — re-running the converter is always safe; `devices.yaml` (id, name, kind, local/cloud, room reference, position in meters, later the Hub entity-id mapping) is **hand-maintained and never touched by the converter**. A single merged file was rejected: merging hand data into regenerated structure needs a round-tripping YAML dependency and turns every room rename into a potential data-loss event. Devices-as-furniture-markers in the drawing was rejected because device metadata doesn't fit a furniture name and regeneration would own hand data. Room ids are slugified from drawn room names ("Living Room" → `living-room`) and must stay stable; the loader (`panel/lib/data/house_loader.dart`) rejects a `devices.yaml` entry referencing a missing room — the converter never reads `devices.yaml`.

Geometry rules (grilled 2026-07-30): meters, one origin (house NW corner) shared by all Floors, x east, y south. Room footprints are rectilinear polygons — right angles only; the house's real 45° walls are squared off by *partitioning* the corner into exactly one room (overlapping rooms are forbidden; upgrading to true 45° edges later costs only converter validation plus one renderer shading case, since footprints are stored as point lists). Rooms tile each Floor completely — every point in exactly one Room; stairs, halls and the attached garage are Rooms. A Floor's slab renders as the union of its rooms, so partial upper floors and the protruding garage need no perimeter concept. Walls are first-class data taken from what is drawn: no wall drawn = open passage = no glass rendered; doors within walls are ignored. The converter rejects diagonals and overlaps, and warns on unwalled room boundaries and non-tiling floors — it never invents geometry. The loader independently enforces the geometry invariants at Panel startup (rectilinear footprints, axis-aligned walls, unique Room and Floor ids, pins inside their Rooms), so the hand-written-YAML escape hatch gets the same guarantees; the contemplated 45° upgrade therefore touches converter + loader + renderer, kept honest by the cross-seam contract test in `panel/test/house_pipeline_contract_test.dart`. Overlap and floor-tiling detection stays converter-only — it is authoring-time work, and the painters tolerate overlap without corrupting anything.

Deferred, enabled by this choice: furniture on the Plan (Sweet Home 3D already stores placements in the same XML — future converter work, no new tool) and multi-floor zoom/scroll Dollhouse navigation (any floor count already fits the schema).
