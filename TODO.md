## 🔴 Carried workarounds — do not remove

Two **upstream go2rtc defects**, both confirmed still present on `master`
(checked 2026-08-10), both **deliberately not filed** — owner decision,
2026-08-10. The Panel carries permanent workarounds instead of waiting for a
fix.

If somebody "tidies" one of these away, the doorbell breaks **silently and
intermittently**, which is exactly how they were found in the first place. Each
is pinned by `panel/test/mse_workarounds_drift_test.dart`.

| Upstream defect | Our workaround | Residual cost |
|---|---|---|
| `pkg/h264/h264.go` — `GetProfileLevelID` accepts only levels `30, 31, 40` and silently falls back to `41`, so a **level-5.0** stream is advertised as **4.1**. Level 4.1 caps a frame at 8192 macroblocks; the doorbell's 1536×1536 is 9216, so a decoder built from that MIME refuses the stream outright — **0 frames**. | `raiseH264Level` in `panel/lib/ui/video/live_video.dart`, applied in `live_video_mse.dart` before `addSourceBuffer`. Unit-tested on the VM. | **None.** A level in a MIME type is a capability hint, so declaring higher is always safe, and the guard returns null (no-op) if upstream ever widens the whitelist. |
| `pkg/mp4/muxer.go` — `AddTrack` seeds every **new consumer's** `pts` at `0`, so the first sample handed to a consumer joining an **already-running** stream gets a placeholder duration and the decoder quits. Cold open works; refresh-and-reopen fails. | Bounded reconnect (`_reconnect`, 3 attempts) — the same thing go2rtc's own player does, which is why *it* survives this and we did not. | **Real and ongoing.** A visible reload, each retry is another Ring session (#177014), and it is probabilistic — it can still give up and fall back to the still photo. |

Full investigation, including the **six theories that were wrong**:
[`hub/dev/go2rtc/DEBUGGING.md`](hub/dev/go2rtc/DEBUGGING.md).
